## Service placement

## Verdict: THREE new services, not four. Staff folds into product-service.

Ports verified by reading every `tcpSocket: { port: N }` in `deploy/k3s/base/services.yaml`. In use: 8101 order-manager, 8102 order-tracking, 8103 product, 8104 notifications-manager, 8108 app-notification, 8109 connector-settings, 8110 email, 8111 push, 8112 sms, 8115 accounting, 8116 whatsapp, 8117 onboarding, 8118 transfer, 8888 config. The domain designs proposed COLLIDING ports (inventory 8119; pos 8119 or 8120; staff 8121; reporting 8121). Final:

| service | port | schema | db role | ingress prefix |
|---|---|---|---|---|
| inventory-service | 8119 | `inventory` | `inventory_service` | `/api/inventory` |
| pos-service | 8120 | `pos` | `pos_service` | `/api/pos` |
| reporting-service | 8121 | `reporting` | `reporting_service` | `/api/reports` |

### ACCEPTED — pos-service (8120)
- **Bounded context.** `orders/V10__orders.sql:18` makes `delivery_address` NOT NULL; `OrderStatus` is PLACED→…→DELIVERED where READY dispatches a carrier (`OrderService.applyTransition`); `Payment.onDelivered` settles cash only at delivery. A counter sale has no address, no rider, is paid now. Faking it through `Order` puts a walk-in on the rider board and into `accounting-service/.../event/OrderEventListener.java`, which pays merchant/carrier/platform shares on `order.delivered`.
- **Write profile.** Hundreds of sales/day, every add-line a write. product-service is read-heavy, `hikari.maximum-pool-size: 10`, `ddl-auto: validate` (verified `services/product-service/src/main/resources/application.yml:28-30, 49-54`).
- **Cross-repo.** order-manager builds from its own repository (root `pom.xml` documents why it is excluded from `<modules>`), so any POS change there is a two-repo release.
- Emits **no** `order.*` event, so order-manager, order-tracking, accounting settlement and product-service's `delivered_order_lines` projection are untouched by construction.

### ACCEPTED — inventory-service (8119)
- Stock is an **append-only ledger with a running balance**, written on every POS line, every delivery order placed/cancelled/delivered, every adjustment and count line. Putting `on_hand` on `products` makes every sale an UPDATE of the row the storefront reads under `idx_products_active_category` (`V10__catalog.sql:43-44`).
- It has its own consumers (`order.#`, `pos.#`) and its own aggregate — exactly the "own queue, own projection" boundary product-service already draws for `delivered_order_lines` (`V22`, `OrderEventListener.java`).
- Schema-per-service is physically enforced (`postgres-init/02-service-roles.sql:1-6`, verified), so it cannot join `products`; it keeps a `catalog_items` projection off `product.*`.

### ACCEPTED — reporting-service (8121)
- No existing service can answer "revenue/orders/items by day and by category across POS + delivery". accounting is a balance-checked ledger settling only `order.delivered` with COLLECTED/CAPTURED; order-manager knows no POS and is cross-repo; product-service's `delivered_order_lines` deliberately keeps no price.
- Month-long `GROUP BY` scans must not share the POS write pool. This is the only service that legitimately reads both event streams.

### REJECTED — staff-service. Staff lives in product-service (`V27__store_staff.sql`).
The staff design argued for its own deployable. I overrule it:
1. **The dependency it avoids already exists.** Its case was "putting it in product-service makes POS depend on the catalog for authorization". But pos-service *already* calls product-service synchronously on every add-line for `GET /api/products/{id}` + `POST /api/products/{id}/price` (the `ProductCatalogClient` idiom). The coupling is unavoidable and already paid for.
2. **The enforcement mechanism is identical either way.** Every enforcing service keeps a local `store_access_projection` fed by `staff.member_changed` regardless of who owns the write side. Only the aggregate's home is in question.
3. **`stores` is the aggregate root and it lives in product-service.** A standalone staff-service needs a `stores` cache table pulled over REST (its own design includes one) — a projection of data sitting in the next schema.
4. **The workload does not justify it.** Its own design says "a few writes a day, reads on login". That earns no isolation, and costs a full deploy pass, a schema/role/Vault/ingress/CI slot, plus a REST hop.

This is the one place I reduce service count, and only because the isolation buys nothing. Staff writes are negligible against product-service's pool; `staff_members` joins `stores` locally; product-service publishes `staff.member_changed` through the outbox it already runs.

### Authorization topology (settled)
`Permission` is a **7-value coarse wire vocabulary** (the two Figma frames draw exactly seven toggles). The 10 fine-grained internal permissions from Understanding 3 never leave a service. product-service resolves effective permissions and publishes them **already resolved**, so no consumer re-implements role logic:

```
staff.member_changed {storeId, merchantId, memberId, userRef, role, status,
                      permissions:[...resolved...], removed, version, occurredAt}
```
Each of pos/inventory/reporting keeps `store_access_projection` upserted `WHERE stored.version < excluded.version`, with a 60s-cached sync fallback `GET /api/stores/{storeId}/staff/me` for the seconds between "added" and "relayed". One `StoreAccess.require(storeId, Permission)` component per service; controllers never branch on role.

### Staff onboarding: invite-code redemption, NOT owner-typed-email account minting
The staff design routed account creation through `POST /api/onboarding/staff-accounts`, exposing Keycloak user creation to any MERCHANT. Its own risk list calls that a spam vector. Rejected. Instead: owner creates an invite (`POST /api/stores/{id}/staff/invites` → 8–12 char code, 24h TTL); the employee signs up through the existing customer path and calls `POST /api/stores/staff/accept {code}` with their own token; the row binds to `CurrentUser.requireId()`. No new Keycloak admin surface, no email-deliverability dependency, no cross-service hop, and the employee proves identity themselves. The Figma email field is kept as a contact/label column, not an account trigger. `MERCHANT_STAFF` realm role is still required so the shells can route and `hasAnyRole('MERCHANT','MERCHANT_STAFF')` admits staff.

### Categories: store-owned rows in product-service
Figma 94:351 ("Add Category", drag-to-reorder, merchant-authored names like "Lebanese Specialties") requires merchant-owned sections. Verified `Category.java` has only `id, name, parentId, imageRef, vertical, createdAt` — no store, no position; and `CategoryController` POST is BACKOFFICE-only. So `categories` gains nullable `store_id` + `position`. The client-contract design's alternative (overload `Aisle` with write semantics) is rejected: aisles are a read projection with no create/rename/delete/image surface. `GET /api/stores/{id}/aisles` keeps its shape and simply sorts by position.

### Correction to a claim repeated by FOUR domain designs
Every one of them asserts that `deploy/k3s/scripts/render-overlays.sh` does not exist and that `overlays/dev/ingress.yaml` and `overlays/qa/ingress.yaml` must be hand-edited in lockstep. **This is false.** The script exists and I read it: it `sed`s `__API_HOST__`/`__IAM_HOST__`/`__PORTAL_HOST__`/`__MON_HOST__` into per-env files from `overlays/ingress.template.yaml`. Edit the template once and run `sh scripts/render-overlays.sh` from `deploy/k3s`. Hand-editing the rendered files is the actual drift hazard. This retires a "risk" from four designs.


## Data model & migrations

## Money model — settled, exact

Verified state: `order-manager` and `product-service` serialize `BigDecimal` as **JSON numbers**; `accounting-service` emits money as a **2-decimal string** (`StatementController.java:437` — `Statement.money(amount).toPlainString()`). No global Jackson money config exists. Both formats already coexist. The client has `Money` (`statement_models.dart:18-43`), a string wrapper that *refuses* JSON numbers and exposes exact `minorUnits`.

**Rule for all three new services (overrides the client-contract design's "LAW 1: money is double"):**
- **Internal, pos-service:** `long` minor units. USD = cents (`*_cents`), LBP = whole pounds (`*_lbp`). Value objects `UsdCents(long)` / `Lbp(long)`. No `double`, no `BigDecimal` arithmetic in the POS domain. POS is the only place doing division (VAT, pro-rata refund allocation, LBP conversion, change), so rounding policy must be explicit and remainders assigned.
- **Internal, reporting/inventory:** `numeric(12,2)` / `BigDecimal`. Postgres `numeric` sums exactly, and these services only add.
- **Wire, all three:** USD as a JSON **string** with exactly two decimals (`"10.55"`); LBP as a JSON **integer**; rate as a JSON **integer**.
- **Client:** reuse the existing `Money` type for every new merchant-suite USD figure.

Why string over double: `Money`'s own doc comment is the argument ("a double cannot hold 0.10, and the error compounds the moment anything adds two of them"). A receipt and a Z-report are pay-grade figures. One rule across all three services means no screen mixes representations. **Documented consequence:** the dashboard shows legacy `MerchantSummary.money` (double, order-manager) beside new `ReportTotals` (Money). Separate cards, never summed client-side.

### Exact arithmetic (pos-service `MoneyMath`)
```java
/** HALF_UP away from zero, exact integer division. den > 0. Handles refund negatives. */
static long divHalfUp(long num, long den) {
    return num >= 0 ? (2*num + den) / (2*den) : -((-2*num + den) / (2*den));
}
static long lbpExact(long cents, long rate) { return divHalfUp(cents * rate, 100); }
static long lbpFace (long cents, long rate) { return divHalfUp(lbpExact(cents,rate), 1000) * 1000; }
static long centsForLbp(long lbp, long rate) { return divHalfUp(lbp * 100, rate); }
static long tax(long netCents, int rateBp)   { return divHalfUp(netCents * rateBp, 10_000); }
```
Verified against Figma 94:859 (rate 90,000):
- Subtotal $9.50, TVA 11%: `tax(950, 1100)` = (2·1,045,000+10,000)/20,000 = **105** = $1.05. Total $10.55. ✔
- `lbpExact(1055, 90000)` = 94,950,000/100 = **949,500 LBP**. ✔
- Change $9.45: `lbpExact(945,90000)` = **850,500 LBP**. ✔
Because `rate % 100 == 0`, cents→LBP is always exact.

**Catalog boundary:** `price.movePointRight(2).setScale(0, RoundingMode.UNNECESSARY).longValueExact()`. A catalog price that is not a whole number of cents is a rule violation, never silently rounded.

**Rate:** integer, `@Value("${delivery.market.lbp-per-usd:90000}")` — the same key `MarketController` and `TransferService` read (`MARKET_LBP_PER_USD` in `configmap-common.yaml`). Snapshotted onto the sale at OPEN, never re-read for that sale (the `transfer/V1__money_transfers.sql` `rate_used` policy).

**Cash vs print:** the receipt prints the **exact** conversion (`total_lbp_exact`) — this is what Figma draws. Physical LBP handed over is rounded to the 1,000 note (`TransferService.lbpFaceFor`, verified: `multiply(rate).divide(1000, 0, HALF_UP).multiply(1000)`); the difference `face − exact`, always within ±500, is booked as `cash_rounding_lbp` so the books still sum exactly.

**VAT:** computed ONCE on the **discounted** subtotal: `tax = tax(subtotal − discount, vat_rate_bp)`, `total = subtotal − discount + tax`. Per-store `vat_rate_bp` default **0** (most dekkanes are below the registration threshold). The Figma "Prices Tax-Inclusive" toggle is stored as `prices_tax_inclusive` but **must be false in phase 1** and renders disabled — inclusive pricing changes the meaning of every catalog price and would have to be mirrored in order-manager or the same product is taxed differently by channel.

### reporting-service `V10__sales_facts.sql` (abridged)
`sales_facts` — **PK is the source's own id** (order id or sale id) so at-least-once redelivery upserts rather than double-counts. `source DELIVERY|POS`, `reference`, `status`, `gross_value`, `goods_revenue`, `discount_amount`, `delivery_fee`, `refunded_amount`, `items_count`, `payment_method`, `occurred_at`, and `local_day date` **fixed at ingest** in `delivery.platform.zone` (Asia/Beirut) so a zone change never restates history. `sales_fact_items` (line_no, product_id, product_name, `category_id`, qty, unit_price, line_total, refunded_qty) + `gin (product_name public.gin_trgm_ops)` for "search by items".

**Revenue definitions, documented on the DTO and never mixed:**
- `goodsRevenue` — DELIVERY = `subtotal` (what accounting settles the merchant on); POS = `subtotal − discount`. This is the headline "Revenue".
- `grossValue` = `totalAmount` (what the customer paid). Secondary figure only.
- `netRevenue = goodsRevenue − refunded`. VOIDED rows are listed but never summed.

No daily rollup table in phase 1: one shop over ≤92 days is a few thousand rows under `idx_facts_store_day`.

### Live-cluster bootstrap (MANDATORY, per new service)

then `POST http://config-server:8888/actuator/busrefresh` from inside the cluster. Verified shape: `config.config_properties` holds exactly these two rows per service (product-service has them plus a minio endpoint override). Mirror all of it into `postgres-init/01,02,03` for future rebuilds.

### Backward-safety summary
Every product-service change is a nullable column, a defaulted NOT NULL column, or a constraint swap provably equivalent for all existing rows. New tables live in new schemas. Older Flutter builds keep parsing (`Product.fromJson` ignores unknown fields). `ddl-auto: validate` means **entity and migration must ship in the same release** or the pod crash-loops in dev and qa.

**Rollback:** dropping a new service = `DROP SCHEMA <s> CASCADE` + delete its two config rows. Nothing else references it; `pos.#`/`inventory.#` are additive routing keys no existing queue binds. If inventory-service is removed for good, run `UPDATE products SET in_stock = true`.

1. MIGRATION NUMBER COLLISION. Three product-service migrations (V25 SKU, V26 categories, V27 staff) land from separate branches. Live high-water is V24, verified. out-of-order:true tolerates gaps but NOT duplicates — two branches both numbering V25 fail Flyway validation at boot in dev and qa. ## Verification verdicts (REQUIRED FIXES)

### holds=false — MONEY CORRECTNESS: the POS money model (dual USD/LBP at rate 90000, cash/card, refunds/voids, totals) is exact — no float rounding drift, mi

Much of the spec verifies. I confirmed, by reading the files: accounting emits money as a 2-decimal string (`services/accounting-service/.../api/StatementController.java:435-437` — `Statement.money(amount).toPlainString()`; `Statement.java:154-155` — `setScale(2, HALF_UP)`); the Dart `Money` refuses JSON numbers and exposes int `minorUnits` (`clients/packages/delivery_core/lib/src/models/statement_models.dart:9-60`); no global Jackson money config exists (grep for `WRITE_BIGDECIMAL_AS_PLAIN`/`Shape.STRING` across `services/` returns only an unrelated onboarding field); `MerchantSummary.platformFees`/`savedByOffers`/`TopProduct.revenue` are `double` (`summary_models.dart:70-106`); the rate key is real and shared (`deploy/k3s/base/configmap-common.yaml:45` `MARKET_LBP_PER_USD: "90000"`; `product-service/.../api/MarketController.java:32`; `transfer-service/.../service/TransferService.java:41`); `lbpFaceFor` is exactly as quoted (`TransferService.java:64-67`). The `MoneyMath` arithmetic is also correct as written: `divHalfUp` is genuine HALF_UP-away-from-zero, overflow is unreachable at realistic magnitudes, and all three Figma 94:859 worked examples recompute exactly (tax(950,1100)=2,100,000/20,000=105; lbpExact(1055,90000)=949,500; lbpExact(945,90000)=850,500).

It still fails, at one specific place, and the platform's own schema is what proves it.

**1. The LBP→USD direction is not exact, has no precedent, and has no rounding account.** The spec's exactness proof is `rate % 100 == 0`, which establishes only that **cents→LBP** is exact. The inverse is exact iff `(lbp*100) % rate == 0`, i.e. `lbp % 900 == 0` at rate 90000. Physical lira come in multiples of 1,000 (the spec's own `lbpFace` rounds to the 1,000 note; `TransferService.java:44` has `rider-change-limit-lbp:100000`), and `1000 % 900 != 0` — so a tenderable LBP amount is essentially **never** a whole number of cents. Yet the spec puts that direction on the wire: `{method:"CASH_LBP", tenderedLbp: 950000}` plus `centsForLbp(lbp, rate) = divHalfUp(lbp*100, rate)`.

Concrete drift, split tender on a $23.50 sale: `CASH_LBP 500,000` + `CARD`. `centsForLbp(500000, 90000) = divHalfUp(50,000,000, 90,000) = 100,090,000/180,000 = 556`. True value 555.5555¢. The drawer holds 500,000 LBP; the sale books **556¢** against it. Card covers 2350−556=1794, so `Σ applied == total` passes, `chk_sale_total` passes, the shift reconciles. **0.44¢ of revenue exists nowhere.** The spec's only rounding sink is `cash_rounding_lbp bigint CHECK (BETWEEN -500 AND 500)`, denominated in **LBP** and defined as `face − exact` for change handed over. There is no `*_cents` counterpart. So "the difference face − exact … is booked as `cash_rounding_lbp` so the books still sum exactly" books one of the two rounding sites and asserts the other away.

**2. The platform already solved this, in the opposite direction, and the spec cites that file while contradicting it.** `services/transfer-service/src/main/resources/db/migration/transfer/V1__money_transfers.sql:3-6`: "the LBP side is the SPLIT the customer chose, **stored as its USD value** (`split_usd + split_lbp_in_usd = amount_usd` exactly, no rounding gap between columns) … The lira face value a rider collects is computed from those two, never stored a second time to drift" — enforced by `chk_transfer_split_sums CHECK (split_usd + split_lbp_in_usd = amount_usd)` (line 27). `grep` for any LBP→USD division across `services/` returns **zero hits**: no service in the platform has ever converted lira into dollars. The spec invokes "the `transfer/V1__money_transfers.sql` `rate_used` policy" for rate snapshotting while inverting the very policy that file exists to state.

**3. `Σ applied must equal total EXACTLY` is unsatisfiable for pure LBP cash — on the spec's own worked example.** For a CASH_LBP tender to be exact at $10.55: `round-half-up(lbp/900) = 1055` → `lbp ∈ [949050, 949950)`. That interval is 900 wide and contains **no multiple of 1,000** (949,000 is below, 950,000 above). So the Figma 94:859 receipt cannot be paid in lira notes. Generally the interval is narrower than the note granularity, so ~10% of totals have no exact LBP tender at all. The spec presumably intends `applied = min(outstanding, value)` with change — but it never says so, and the two readings differ materially: computing change in **LBP space** gives `950,000 − lbpExact(1055) = 500` LBP → face 1,000 → rounding 500 (in band); computing it in **cents space** gives `centsForLbp(950000)=1056 − 1055 = 1¢` → 900 LBP exact → face 1,000 → rounding 100, and the drawer is short 500 LBP that nothing records. 400 LBP of divergence on the spec's own example, from an unstated choice.

**4. Missing CHECKs let a CASH_LBP row be money-incoherent.** `chk_payment_cash_usd` constrains `tendered_cents >= applied_cents` for CASH_USD; there is **no counterpart for CASH_LBP**. A row with `applied_cents = 2350`, `tendered_lbp = NULL` satisfies every constraint listed. And `chk_payment_noncash` forces `change_cents = 0 AND change_lbp = 0` only for non-cash — nothing stops a cash row carrying change in **both** currencies simultaneously.

**5. Rate typing is a shared-config landmine.** `@Value("${delivery.market.lbp-per-usd:90000}")` bound to `long`, but the identical key binds to `BigDecimal` in `MarketController.java:32` and `TransferService.java:41`, and `transfer/V1:16` stores `rate_used NUMERIC(12,2)` — the platform schema explicitly permits a fractional rate. Setting `MARKET_LBP_PER_USD: "89500.50"` in `configmap-common.yaml:45` leaves product-service and transfer-service healthy and **crash-loops pos-service** at context startup. The whole exactness argument also rests on `rate % 100 == 0`, which nothing in config, schema, or code enforces.

**6. Two citation defects.** (a) `chk_order_total` **does not exist**. The real constraints are `chk_order_total_positive` (`orders/V10__orders.sql:29`, redefined `V22__promo_codes.sql:160-161`) and `chk_order_total_is_subtotal_plus_fee` (`V11__delivery_fee.sql:31`, redefined in V21:103-104, V22:135-136, V26:35-36). (b) "consistent with how the existing platform represents order money" is overstated: order money is `numeric(12,2)` + `BigDecimal` domain arithmetic (`orders/V10__orders.sql:17,53`; `Order.recomputeTotal` at `Order.java:477-484`), and order-manager and product-service serialize `BigDecimal` as JSON **numbers**. The 2-decimal-string wire rule matches accounting-service alone.

**7. Refund allocation is under-specified in a way that does not sum.** "remainder assigned to the last line so the parts sum to the whole" is well defined for one full refund, but refunds here are per-line and sequential. If the remainder-bearing last line is refunded in a later call than the others, and each call recomputes shares from the live `subtotal`/`discount`, the shares drift; if it is never refunded, the residual is stranded. The rule needs shares fixed once, at completion.

The arithmetic core is sound. The boundary where lira enters as lira is not, and it is not exact, not fully constrained, and not consistent with `money_transfers`. Default is `holds=false` and this clears that bar concretely.

**REQUIRED FIX:**

Make lira enter the POS the way the platform already takes it — as a USD amount settled in lira — so the inexact LBP→USD direction never exists.

**F1. Delete `centsForLbp` from `MoneyMath`. Re-shape the CASH_LBP tender.**
```
{method:"CASH_LBP", amount:"10.55"}      // USD 2-dec string: the portion settled in lira
                                          // mirrors money_transfers.split_lbp_in_usd
```
Server derives, never accepts: `lbp_due_exact = lbpExact(applied_cents, rate)`, `lbp_to_collect = lbpFace(applied_cents, rate)`. `applied_cents` is then an exact integer by construction, `Σ applied == total` is satisfiable for every total, and the $10.55 case is payable. Keep `tendered_lbp` as what the cashier physically received, for drawer reconciliation only — never as the source of `applied_cents`.

**F2. Add the missing CHECKs to `sale_payments` so the lira books close by construction.**
```sql
lbp_due_exact bigint, lbp_collected bigint, change_lbp bigint NOT NULL DEFAULT 0,
cash_rounding_lbp bigint NOT NULL DEFAULT 0,
CONSTRAINT chk_payment_cash_lbp CHECK (method <> 'CASH_LBP' OR
    (lbp_due_exact IS NOT NULL AND lbp_collected IS NOT NULL AND lbp_collected >= 0)),
-- the identity that makes every lira rounding land in the rounding account:
CONSTRAINT chk_payment_lbp_closes CHECK (method <> 'CASH_LBP' OR
    lbp_collected - change_lbp - lbp_due_exact = cash_rounding_lbp),
CONSTRAINT chk_rounding CHECK (cash_rounding_lbp BETWEEN -500 AND 500),
-- change is handed back in exactly one currency:
CONSTRAINT chk_change_one_currency CHECK (change_cents = 0 OR change_lbp = 0)
```
